Nightly E2E Failure Pipeline

Automated pipeline that detects nightly E2E test case failures, analyzes root causes, attempts fixes, and escalates when fixes don't work. Fully automated via GitHub Actions for the upstream repo.

Summary

9
Pipeline phases
2
Max fix attempts
~105m
Worst-case runtime
$0
GH Actions cost

The pipeline runs as a single GitHub Actions job on a daily cron schedule. It detects nightly failures by checking GCS artifacts, runs a single AI agent (e2e-fix) that analyzes root causes, creates or updates GitHub issues for tracking, implements fixes, triggers OpenShift CI on the fix PR, and polls for results. If the fix passes CI, the pipeline requests review and labels the PR for merge. If two fix attempts fail, the pipeline escalates: it skips the failing test case and creates a JIRA bug for tracking.

Cost: The upstream repo is open source. GitHub Actions minutes are free and unlimited for public repositories. The ~40-minute CI polling wait costs nothing — the runner sleeps between polls. The 6-hour per-job hard limit accommodates the full two-iteration pipeline comfortably.

Decision Tree

Every decision point in the pipeline, who makes it, and what each outcome triggers.

Decision point Who decides Outcomes
Did the nightly fail? GH Actions ● Passed → Exit. Nothing to do.
● Failed → Run the e2e-fix agent with prow URL.
What is the fix_category?
Classification after analysis		 Agent ● infra_flake → Log and exit. Transient, no action needed.
● product_bug → Create GH issue. No fix — root cause is in plugin source.
● environment → Create GH issue for visibility. Cluster/OCP problem.
● test_fix → Create/update issue, then proceed to fix.
Existing issue or fix PR?
Unified dedup for all non-infra categories		 Skill ● Fix PR exists → Comment on issue: "still failing, PR pending merge." Stop.
● Issue exists (no PR) → Comment with new analysis. If test_fix → attempt fix. If product_bug/environment → done.
● Nothing exists → Create new issue. If test_fix → attempt fix. If product_bug/environment → done.
Is the analysis correct?
Verify against actual code		 Agent ● Yes → Implement the fix as suggested.
● Partially → Use valid parts, reason from code for the rest.
● No → Ignore analysis. Reason independently from code and error.
Did CI pass?
Poll gh pr checks every 5 min		 GH Actions ● Passed → Close issue. Label PR ready-to-merge. Request review. Done.
● Failed → Check attempt count to decide next step.
Attempt count < max (2)?
Read from issue labels		 GH Actions ● Yes (retry) → Extract prow URL from check detailsUrl. Re-analyze. Update PR. Trigger CI again.
● No (max reached) → Escalate: add test.skip, create JIRA bug, close issue.
Iteration strategy?
Agent reads prior attempts from issue		 Agent ● Same root cause → Refine the previous fix — address what attempt 1 missed.
● Different problem → First fix revealed a new issue. Try a different approach.

Architecture Agent + Skills

The agent makes all judgment calls: classifying failures, deciding fix strategy, and choosing when to escalate. Skills provide reusable procedures for specific tasks — how to read prow artifacts, how to manage GitHub issues, how to interact with JIRA.

e2e-fix agent — the brain

Mission: fix nightly E2E failures or escalate. Decides what to do and when.

e2e-failure-analysis

skill

How to fetch GCS artifacts, read pod logs, events.txt, previous pod logs, and trace root causes.

gh-issue-ops

skill

How to dedup-check, create, comment on, label, and close GitHub issues.

jira-ops

skill

How to create RHDHBUGS tickets via ACLI with the right fields and cross-references.

Agent decides vs Skills instruct

Agent decidesSkills provide
Is this a test_fix, product_bug, or infra_flake? How to fetch and parse prow artifacts
Is the analysis actually correct? (verify against code) How to search for duplicate issues
What is the smallest correct fix? How to create well-structured GitHub issues
On retry: same approach or pivot? How to create JIRA bugs via ACLI
When to give up and escalate to skip How to format skip comments for grep-ability

Same SKILL.md, both environments. The agent and skills run identically in a fullsend sandbox (GH Actions) or locally via Claude Code. The only difference is credential plumbing — fullsend uses harness YAML + post-scripts; local uses the user's gh auth and ACLI config.

Phase 1: Detect Failure GH Actions

The GitHub Actions cron job checks GCS for the latest nightly run per branch. Same pattern as the existing Overlay-alerts.gs script.

# For each configured branch (main, release-1.10):

GCS_BASE="https://gcsweb-ci.apps.ci.l2s4.p1.openshiftapps.com/gcs/test-platform-results/logs"
JOB_NAME="periodic-ci-redhat-developer-rhdh-plugin-export-overlays-${BRANCH}-e2e-ocp-helm-nightly"

# 1. List latest run ID from GCS directory listing
# 2. Fetch results.json from latest run
# 3. Check stats.unexpected > 0 (failures exist)
# 4. If failed → extract prow URL → proceed to ANALYZE
All tests passed

Nothing to do. Log success and exit.

Tests failed

Extract prow URL. Proceed to Phase 2 (Analyze).

Phase 2: Analyze Agent + Skill

The agent uses the e2e-failure-analysis skill to investigate the prow failure. The skill walks through the GCS artifacts — Playwright results, pod logs, cluster events, previous pod logs — and traces the root cause. The agent then classifies the failure and writes a structured result.

Input

Prow URL pointing to the failed nightly run

Output

agent-result.json with root cause, failed test cases, remediation, and fix_category

What the skill covers: Playwright results.json parsing, pod restart investigation (events.txt, previous pod logs), config and timeout analysis, missing plugin detection. See e2e-failure-analysis/SKILL.md for the full methodology.

Phase 3: Classify Agent judgment

Based on the analysis, the agent classifies the failure into one of four categories. This determines how far the pipeline goes — only test_fix proceeds to a fix attempt.

CategoryMeaningPipeline action
test_fix Fixable in test specs or deployment config Dedup check → create/update issue → fix → PR → CI
product_bug Root cause is in plugin source code Dedup check → create/update issue only. No fix attempt.
infra_flake Transient infra/cluster issue Log and exit. No issue, no fix.
environment OCP/cluster misconfiguration Dedup check → create/update issue for visibility. No fix attempt.

Phase 4: GitHub Issue Agent + Skill

All non-infra failures (test_fix, product_bug, environment) pass through this phase. The agent uses the gh-issue-ops skill to check for existing work and create or update a tracking issue on the upstream repo.

Check for open fix PR

If a fix PR already exists for this test case (from a previous nightly run that hasn't been merged yet), the pipeline stops here. Comments on the existing issue: "Nightly still failing. Fix PR #N pending merge."

stops pipeline if PR exists

Issue dedup check

Searches for an existing open issue for the same failing test case. Prevents creating duplicates across nightly runs.

Create or comment

No existing issue

Create a new issue with the full analysis: root cause, prow URL, fix_category, failed test cases.

Issue already exists

Comment on it with the new analysis. Adds fresh data to the coordination log.

Route by category

Only test_fix continues to Phase 5 (Fix). For product_bug and environment, the pipeline stops here — the issue is tracked but no fix is attempted.

Issue repo: Upstream (redhat-developer/rhdh-plugin-export-overlays). Issues are visible to the whole team, not just the fork owner.

Phase 5: Fix Agent

Only runs when fix_category = test_fix. The agent reads the analysis, verifies it against actual code, and implements the smallest correct change.

Verify analysis against code

Read the spec file, config files, and test utils. Confirm the diagnosis is correct. If the analysis is wrong, reason from the code and implement the correct fix instead.

zero-trust

Implement fix

Modify test specs, playwright config, deployment config. Every line in the diff must be justified by the failure analysis.

✓ workspaces/*/e2e-tests/ ✓ deployment config ✗ plugin source ✗ CI config

Verify locally

Run linters, type checks, any available local validation from the repo's CLAUDE.md or Makefile.

Commit

Stage only changed files (never git add -A). Conventional commit on fix/e2e-<slug> branch. Always new commit, never amend.

Phase 6: Push + PR Fullsend or Local

The fix is committed on a feature branch. This phase pushes it to the fork and creates a cross-fork PR on upstream. The issue is updated with the PR link and an attempt label.

Fullsend (GH Actions)

Agent comments on the issue summarizing what it fixed.

post-e2e-fix.sh runs on host after sandbox:

1. Push branch to fork

2. Create cross-fork PR on upstream

3. Comment on issue with PR link

4. Add attempt:N label to issue

Local

Agent does everything directly:

1. Push branch to fork

2. Create cross-fork PR on upstream

3. Comment on issue with fix summary + PR link

4. Add attempt:N label to issue

Cross-fork PR: The PR is created from subhashkhileri/rhdh-plugin-export-overlays:fix/e2e-<slug> targeting redhat-developer/rhdh-plugin-export-overlays:main (or release-1.10).

No review request yet. The PR is not labeled ready-to-merge at this point — CI hasn't run. Review request and labeling happen after CI passes in Post-Pipeline.

Phase 7: Monitor CI GH Actions

After the PR is pushed, the pipeline triggers OpenShift CI on the PR, waits for the result, and routes to the next step.

Trigger CI

The GH Actions bot comments /test e2e-ocp-helm-nightly on the PR. The GH_TOKEN must belong to a trusted org member — prow checks author_association before accepting the command.

Poll for completion (~40 min)

The workflow polls the PR's status checks every 5 minutes until the e2e check completes. The runner sleeps between polls — costs nothing on public repos.

Extract result

If CI failed, the prow URL is extracted from the check's detailsUrl field — no GCS listing needed.

CI passed

Close issue → Post-Pipeline

CI failed

Check attempt count → Iterate or Skip

Local path: The user handles this phase manually — comments /test e2e-ocp-helm-nightly on the PR, waits for CI, then invokes /fs-e2e-fix iterate <prow-url> --issue N with the new failure URL.

Phase 8: Iterate attempt < 2

When CI fails and attempts remain, the pipeline starts a fresh agent run — fullsend has no session persistence, so the previous run's context is gone. The iteration follows the same phases (Analyze → Fix → Push → Monitor) with these key differences:

What's differentFirst runIteration
Prior context None needed Agent reads issue comments to learn what was tried before no session persistence
Analysis Analyze the nightly failure Analyze the new CI failure (different prow URL, extracted from check detailsUrl)
Fix strategy Implement based on analysis Agent judgment: refine the previous fix, or pivot to a different approach agent judgment
Branch Create new fix/e2e-<slug> Checkout existing branch, add a new commit (never amend)
Issue update Create issue, label attempt:1 Comment on issue with new approach, update label to attempt:2

After the updated PR is pushed, the pipeline loops back to Phase 7: Monitor CI to trigger and poll CI again.

Phase 9: Skip + JIRA Escalation attempt = max

When 2 fix attempts have failed, the failure is likely a product bug beyond the scope of test/config changes. The same fix agent runs in FIX_MODE=skip — instead of implementing a fix, it skips the failing test case and creates a JIRA bug for tracking.

Create JIRA bug from issue history

The agent reads the full issue history (all prior analysis, fix attempts, and outcomes) and creates a RHDHBUGS ticket via ACLI.

FieldValue
SummaryTest case name + short root cause
DescriptionRoot cause, fix attempt 1 + outcome, fix attempt 2 + outcome, prow URLs, workspace/plugin name, link to skip PR
Labelse2e-nightly, auto-skip

Add test.skip, commit, and push

The JIRA key goes directly in the skip reason string — grep-friendly for the future stale-skip scanner. New commit on the existing fix/e2e-<slug> branch; the PR updates automatically.

test.skip(
  isNightlyMode,
  "filecheck lock timeout after pod restart (RHDHBUGS-4521)",
);

Label PR, request review, close issue

Add ready-to-merge label and request review from the team — human reviews the skip, sees the JIRA reference, approves. Close the issue with a comment: "Skipped — tracked in RHDHBUGS-XXXX."

Post-Pipeline Lifecycle

By the time the pipeline exits, the issue is closed and the PR is labeled ready-to-merge with a review request. What happens next is human-driven.

Fix PR (CI passed)

Human reviews the fix diff, approves, and merges. Next nightly should pass for this test case.

Skip PR (escalated to JIRA)

Human reviews the test.skip, sees the JIRA reference, approves, and merges. The RHDHBUGS-XXXX bug stays open for the product team to fix in a future release.

After a skip PR is merged: When the JIRA bug is eventually resolved, a stale-skip scanner (future) finds the test.skip with that JIRA key, removes it, and opens an unskip PR.

State Management

All pipeline state lives on the GitHub issue. No local files, no session persistence, no external databases. The issue is the single source of truth across agent runs.

Example: Issue #42 lifecycle

Issue created

Body: root cause analysis, prow URL, fix_category: test_fix

Fix attempt 1

Comment: "Fix attempted in PR #55. Reduced filecheck timeout 15m→2m."

Label: attempt:1

CI failed

Label: attempt:1 → attempt:2

Nightly Dedup

While a fix PR waits for human review/merge, the nightly keeps running and failing on the same test case. The pipeline detects this in Phase 4 — after analysis identifies the failing test case, it checks for an existing open fix PR. If one exists, the pipeline comments on the existing issue ("Nightly still failing. Fix PR #N pending merge.") and stops. No duplicate PRs, no wasted fix attempts.

Stale-Skip Scanner Future

A periodic agent or script that finds skipped test cases whose JIRA bugs have been resolved, and creates PRs to remove the skips.

# Scan for skipped tests with JIRA references:
grep -rn 'test.skip' workspaces/*/e2e-tests/ \
  | grep 'RHDHBUGS-'

# For each JIRA key found:
acli jira getIssue --issue RHDHBUGS-4521 --field status

# If status = Done/Closed:
#   → Remove test.skip
#   → Create unskip PR
#   → Link to the original JIRA

Not built now. The structured skip format (RHDHBUGS-XXXX in the reason string) is the design-for-future that enables this scanner. No extra work needed today.
